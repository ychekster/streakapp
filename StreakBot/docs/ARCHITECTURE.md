# Архитектура StreakBot

Документ описывает ключевые архитектурные решения и причины, по которым они
приняты.

## Компоненты и поток данных

```
                 /start, блокировка бота (my_chat_member)
Telegram ────────────────────► Бот (bot/) ──► приветствие + кнопка Mini App
   ▲                              │           (запустивший бота записывается в БД)
   │                              ├─ раз в минуту: напоминания ◄── БД (tma/backend)
   │                              └─ каждые 3 с: рассылки из админ-панели ◄── БД
   │ кнопка «Открыть приложение» (web_app)
   ▼
Mini App (tma/frontend) — приложение и, для администраторов, админ-панель
   │  HTTP, Authorization: tma <initData>
   ▼
API (tma/backend, FastAPI) ──► Bot API: личные сообщения, ответы на отзывы,
   │                               копия рассылки автору
get_current_user (проверка подписи initData)
   │
get_db_user (запись пользователя; день активности; заблокированному — 403)
   │                         └─ /admin/*: get_admin_user (есть в таблице admins, иначе 403)
Router → Service (привычки, настройки, отзывы; admin.py, analytics.py)
   │
Repository (CRUD)
   │
SQLAlchemy (async session)
   │
SQLite / PostgreSQL
```

Бот и API — два независимых процесса. Общие у них `.env`, `BOT_TOKEN` (бот им
авторизуется в Telegram, API — проверяет подпись `initData` и отправляет сообщения из
админ-панели) и база данных: её ведёт API, а бот через тот же слой данных читает из
неё напоминания и рассылки и отмечает в ней события Telegram — кто запустил бота, кто
его заблокировал, как идёт рассылка.

## Слои и ответственность

| Слой | Где | Отвечает за |
|---|---|---|
| Бот | `bot/*` | `/start`, кнопка Mini App в меню чата, напоминания о привычках, рассылки из админ-панели, отметка блокировки бота |
| Конфиг API | `tma/backend/config.py` | Загрузка и валидация `.env` (pydantic-settings) |
| Авторизация | `tma/backend/auth.py` | Проверка подписи `initData` (HMAC-SHA256) |
| Зависимости | `tma/backend/dependencies.py` | DI: сессия + репозиторий, пользователь Telegram, запись в БД |
| Роутеры | `tma/backend/routers/*` | HTTP-эндпоинты `/tasks`, `/settings`, `/meta`, `/reviews`, `/admin/*` |
| Сервисы | `tma/backend/services.py` | История выполнения, создание/изменение привычки, отметка, настройки, отзывы, наступившие напоминания |
| Админ-панель | `tma/backend/admin.py`, `tma/backend/analytics.py` | Пользователи, отзывы, администраторы, рассылки; аналитика |
| Сообщения из API | `tma/backend/messaging.py` | Личное сообщение, ответ на отзыв и копия рассылки — через Bot API сразу в запросе |
| Валидация | `tma/backend/validation.py` | Проверка названия, частоты, времени напоминания, цвета, часового пояса, языка, темы |
| Часовые пояса | `tma/backend/timezones.py` | Каталог поясов, поиск города, разбор `UTC±N`, подписи на языке интерфейса |
| Справочник городов | `tma/backend/cities.py`, `tma/backend/data/cities.tsv.gz` | ~64 тыс. городов GeoNames с зонами и названиями; поиск по названию |
| Репозиторий | `tma/backend/repository.py` | Единственная точка доступа к БД |
| Модели | `tma/backend/models.py` | ORM-схема (User, Task, TaskLog, Admin, Review, UserActivity, Broadcast) |
| Миграции | `alembic/` | Версионирование схемы |

## Ключевые решения

### Бот — точка входа и напоминания
Вся работа с привычками идёт в Mini App, поэтому у бота нет ни FSM, ни middlewares,
ни команд, кроме `/start`. На `/start` он присылает приветствие и inline-кнопку
`web_app`; та же кнопка стоит в меню чата (`MenuButtonWebApp`). Поэтому `TMA_URL`
для бота обязателен.

- **Напоминания — опрос базы раз в минуту.** Время напоминания привычки задаётся в
  приложении и хранится в `tasks.reminder_time` (в поясе пользователя). Цикл
  `bot/reminders.py` в начале каждой минуты спрашивает `services.due_reminders`, у
  каких привычек время напоминания в поясе владельца совпало с этой минутой, и
  присылает «🔔 Пора выполнить «…»». Напоминание приходит только в запланированные
  дни и только пока привычка за день не отмечена. Из базы читаются не все привычки с
  напоминанием, а только те, чьё время сейчас наступило хоть где-то на Земле
  (несколько десятков значений «ЧЧ:ММ» — по индексу `ix_tasks_reminder_time`), а
  отметки за день проверяются одним запросом. Опрос, а не расписание в памяти
  (как у прежнего APScheduler): привычки меняет другой процесс — API, и так изменения
  подхватываются сразу, без синхронизации и восстановления заданий после рестарта.
- **Каждая минута — один раз.** Цикл помнит последнюю обработанную минуту и, если
  отстал (долгая отправка, пауза процесса), досылает пропущенные — не дальше 5 минут
  назад. При старте обрабатывается и текущая минута: рестарт бота ровно в минуту
  напоминания может прислать его дважды, но не теряет его.
- **Сбой доставки не мешает остальным.** Заблокировавший бота пользователь
  (`TelegramForbiddenError`) и прочие ошибки Telegram логируются; на `RetryAfter`
  бот ждёт и повторяет отправку один раз.
- **Рассылка — параллельно, но в лимитах Bot API.** Каждому пользователю — своя
  очередь с паузой секунда между сообщениями (лимит на чат), а общий «метроном»
  выдаёт не больше 25 отправок в секунду (лимит бота ~30). Места в общей очереди
  выдаются по кругу: сначала по первому напоминанию каждому, потом по второму, —
  поэтому пользователь с десятком напоминаний на 09:00 не задерживает остальных, а
  ожидание `RetryAfter` одного чата не останавливает рассылку.

- **Общий темп отправки.** Напоминания и рассылки отправляет один процесс с одним лимитом
  Bot API, поэтому «метроном» у них один (`bot/pacing.py`): у каждого свой — вдвоём они
  бы лимит превысили.
- **Блокировка бота отмечается в базе** (`users.bot_blocked_at`): Telegram присылает
  `my_chat_member` при блокировке и разблокировке, а 403 при отправке напоминания или
  рассылки подтверждает её. `/start` снимает отметку. По ней считается аналитика
  «заблокировали бота», и заблокировавшим не отправляются рассылки.

- **Разметка через entities.** Жирные заголовок и призыв собираются через
  `aiogram.utils.formatting` (`Text`, `Bold`). Библиотека сама считает смещения
  entities (в UTF-16, с учётом эмодзи), поэтому тексты в `constants.py` хранятся в
  чистом виде, без экранирования и `parse_mode`.
- **Старое меню команд удаляется.** Список команд, зарегистрированный прежними
  версиями бота через `set_my_commands`, хранится на стороне Telegram. При старте
  бот вызывает `delete_my_commands`, чтобы пользователи не видели несуществующие
  команды.

### API — владелец данных
Модели, репозиторий и создание таблиц живут в `tma/backend`. При старте API
создаёт недостающие таблицы (`create_all`, существующие не меняет); схема
версионируется alembic. Бот пишет в базу только события Telegram и ход рассылок — через
тот же репозиторий, своих таблиц у него нет.

### Цвет привычки
У каждой привычки свой цвет (`tasks.color`) — ключ палитры (`blue`, `green`, …),
а не hex: сами цвета — дизайн-токены фронтенда (`--palette-*`), и их можно менять,
не трогая данные. Бэкенд проверяет только, что ключ из списка
`constants.HABIT_COLORS`. Во фронтенде корень карточки или экрана привычки получает
переменную `--habit-rgb`, и всё внутри (сетка, кнопка отметки, иконки показателей)
берёт цвет из неё.

### Регистрация пользователя при первом запросе
Отдельного онбординга нет. Зависимость `get_db_user` вызывает
`Repository.get_or_create_user` по данным из проверенной `initData`: при первом
открытии приложения запись создаётся (если её ещё не создал `/start` в боте), при
последующих синхронизируются @username и имя (если они не изменились, UPDATE не
выполняется). Первый запрос отмечает и первое открытие приложения (`app_opened_at`):
пользователь, у которого его нет, только запускал бота. Вставка обёрнута в SAVEPOINT:
если несколько первых запросов пришли параллельно и один уже создал запись,
остальные ловят `IntegrityError` и перечитывают её. FastAPI кеширует зависимости в
пределах запроса, поэтому `get_db_user` и обработчик маршрута работают с одним
репозиторием и одной сессией.

### Прогресс вычисляется, а не хранится
Отметки хранятся в `TaskLog` (одна запись на задачу и дату). История привычки —
364 булевых значения (сетка 14×26, старое → сегодня; список показывает последние
182) — каждый раз собирается по логам: день закрашен, если в эту дату есть лог со
статусом `done`. Так же, за один проход по логам, считаются текущая и лучшая серии
и общее число выполнений; какие пропуски рвут серию, решает расписание привычки
(`schedule.py`). Единственный источник правды — журнал отметок, рассинхронизация
исключена.

Приложение ставит только `pending` и `done` (переключение отметки за сегодня).
Статусы `skipped` и `missed` проставлял прежний бот; они оставлены в enum, чтобы
читались исторические записи, и в истории считаются невыполненными днями.

### Часовые пояса
«Сегодня» считается в поясе пользователя (`User.timezone`, строка IANA). Пояс
выбирается в настройках приложения городом: пользователь ищет свой город, а пояс —
зона этого города. Город хранится рядом с поясом (`User.timezone_city`, id в
справочнике), потому что у зоны много городов: выбравший Санкт-Петербург видит в
настройках «Санкт-Петербург», а не «Москва».

Справочник городов (`cities.py`) — ~64 тыс. городов от 5000 жителей из GeoNames
(https://www.geonames.org, лицензия CC BY 4.0) с зоной IANA, страной, регионом,
населением и названиями на английском и русском. Кроме них у города есть другие
названия — варианты написания, прежние, на других языках латиницей и кириллицей, — и
поиск идёт по всем («Питер», «Ленинград», «St. Petersburg» → Санкт-Петербург). Файл
`tma/backend/data/cities.tsv.gz` (2,8 МБ) собирает `scripts/build_cities.py` из выгрузок
GeoNames; в репозитории лежит готовый, пересобирать его нужно, только чтобы обновить
данные. Справочник загружается при старте API (около секунды, ~50 МБ памяти). Поиск —
по названиям, склеенным в одну строку (`str.find` вместо перебора), и занимает
миллисекунды; выше — совпадение названия целиком, потом начало названия, потом начало
слова в нём, а при равенстве — город крупнее. Последние слова запроса могут уточнять
страну или регион («портленд орегон»), а у одноимённых городов страны в списке виден
регион.

Без запроса экран выбора показывает каталог `GET /meta/timezones` — по поясу на зону
из `zone.tab` базы tz (pytz), с запада на восток. Город пояса — тот, что дал зоне имя
(для Europe/Moscow — Москва); он же показывается в настройках у тех, кто выбрал пояс
до появления справочника. Зоны без такого города в справочнике (острова, мелкие
города) подписаны по CLDR (библиотека Babel); оттуда же названия стран. CLDR хранит
часть городов под устаревшими именами зон (`Europe/Kiev` вместо `Europe/Kyiv`),
поэтому город ищется и по синонимам зоны. Смещения считаются на момент запроса — с
учётом летнего времени.

Раньше пояс выбирался смещением `UTC±N`; такие значения API по-прежнему принимает и
переводит в `Etc/GMT∓N` (`timezones.parse_utc_offset`; в именах `Etc/GMT` знак
инвертирован), а в настройках показывает как `UTC±N`. Пока пояс не выбран,
используется UTC.

### «Отмечать за вчера»
Режим сдвигает «сегодня» приложения на день назад: `services.user_today` возвращает
вчерашнюю дату, и от неё считается всё — какой день отмечает кнопка, запланирована ли
на него привычка, где кончаются история и серии. Отдельной логики для «вчера» нет,
поэтому фронтенд работает как обычно (оптимистичная отметка меняет последнюю ячейку
сетки). Отметки, поставленные за настоящее «сегодня» до включения режима, не видны до
завтра — тогда они станут вчерашними. Напоминания режим не меняет.

### Язык и тема
Язык интерфейса (`users.language`) и тема (`users.theme`: светлая, тёмная или
адаптивная) хранятся на сервере, как и остальные настройки, — и переходят вместе с
пользователем на другое устройство. Новому пользователю язык выбирается по языку его
Telegram; на этом же языке бот присылает напоминания.

Фронтенд держит все тексты на обоих языках (`strings.ts`) и раздаёт строки текущего
языка через контекст (`preferences.ts`). Ошибки API показываются не текстом сервера
(он на русском), а по коду ошибки — на языке интерфейса. Тёмная тема — те же
дизайн-токены с другими значениями (`:root[data-theme="dark"]`), поэтому компоненты
о темах не знают. Адаптивная тема следует за темой Telegram (`colorScheme`,
`themeChanged`), вне Telegram — за `prefers-color-scheme`. Чтобы язык и тема были
верными с первого кадра, последние значения запоминаются в `localStorage`.

### Repository pattern
Роутеры и сервисы не пишут SQL. Вся работа с БД — через методы `Repository`,
привязанного к одной async-сессии. Сессию на каждый запрос открывает зависимость
`get_repository` и коммитит её по завершении обработчика (откат при ошибке).

Зависимость подключается с областью `"function"` (`RepositoryDep`): FastAPI закрывает её
— и выполняет `commit` — **до** отправки ответа. С областью по умолчанию закрытие шло
бы уже после ответа, и сбой `commit` (например, занятая база) клиент бы не увидел:
получил бы `200` и состояние, которого в базе нет.

Список привычек читает отметки всех привычек одним запросом и только две колонки
(`task_id`, `scheduled_date`), без ORM-объектов: у привычки за годы накапливаются
тысячи отметок.

### База данных: несколько процессов
С базой одновременно работают API и бот (читает напоминания и рассылки, отмечает
события Telegram и ход рассылки). SQLite переводится в режим WAL (`database.py`): читатели не блокируют
писателя, а занятая база ждёт до 15 секунд, а не сразу отвечает «database is locked»
(такая ошибка встречалась в логах прежнего бота). Для PostgreSQL — пул соединений
(`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`) с проверкой соединения перед выдачей. Резервную
копию SQLite снимает `scripts/backup_db.py` (backup API — согласованный снимок вместе
с WAL).

### Админ-панель
Админ-панель — режим того же Mini App, а не отдельное приложение: администратор входит в
неё из настроек (ряд виден, если `GET /settings` вернул `is_admin`), и на это время
экраны и нижняя навигация приложения заменены своими (`AdminApp.tsx`). Панель — только
на английском.

- **Права.** Администраторы — таблица `admins` (id Telegram, без ссылки на `users`: можно
  добавить того, кто ещё не открывал приложение). Каждый `/admin/*` проверяет её через
  зависимость роутера `get_admin_user` (иначе `403 admin_required`) — отдельным запросом,
  а не флагом, поэтому снятые права действуют сразу. Первый администратор
  (`SEED_ADMIN_IDS`) добавляется миграцией `0008` и при старте API в пустой список. Себя
  убрать нельзя — это делает другой администратор, поэтому список не опустеет.
  Администратора нельзя заблокировать или удалить.
- **Активность.** `get_db_user` отмечает запрос (`Repository.touch_user`): время
  последнего визита (`users.last_seen_at`) — не чаще раза в минуту, чтобы каждый запрос
  не был записью в базу, — и день активности (`user_activity`, одна строка на
  пользователя и день по UTC). Из них — «сейчас в приложении», DAU/WAU/MAU и график.
  Миграция восстановила историю активности по дням регистрации и отметкам привычек.
- **Аналитика** (`analytics.py`) считается по запросу агрегатами в базе. Доля выполнения
  по дням — по расписаниям активных привычек: «запланировано на день» — привычки,
  созданные не позже дня, у которых он в расписании (двоичный поиск по датам создания для
  каждого дня недели); «выполнено» — их отметки `done` за этот день. Удалённые привычки
  не учитываются: когда их удалили, база не хранит. Аудитория делится без пересечений:
  пользуются приложением, ещё не открывали, заблокировали бота.
- **Поиск пользователей** — `ILIKE` по имени и @username (и начало id для цифр).
  Встроенная `lower()` SQLite знает только латиницу, поэтому `database.py` заменяет её на
  каждом соединении Python-версией — поиск без учёта регистра работает и для кириллицы,
  как в PostgreSQL.
- **Страницы списков.** Отзывы — курсором по id (новые сначала). Пользователи — смещением:
  они отсортированы по `created_at`, а у значений из разных источников (серверное
  `CURRENT_TIMESTAMP` и Python) в SQLite разный текстовый формат, поэтому сравнение «после
  такой-то записи» ненадёжно. Фронтенд не дублирует уже показанные строки.
- **Блокировка и удаление.** Заблокированному (`users.blocked_at`) API отвечает
  `403 user_blocked`, напоминания и рассылки ему не отправляются. Удаление стирает
  пользователя со всеми отметками, привычками, отзывами и днями активности; если он снова
  откроет приложение, начнёт с чистого листа.
- **Личные сообщения и ответы на отзывы** API отправляет сам (`messaging.py`) — сразу, в
  запросе администратора, чтобы тот видел результат. Что пользователь заблокировал бота
  или не запускал его, — не ошибка, а ответ «не доставлено»: при ошибке транзакция
  откатилась бы вместе с отметкой о блокировке. Ответ на отзыв приходит с заголовком на
  языке пользователя и цитатой отзыва.
- **Рассылки** долгие и должны переживать перезапуск, поэтому API их только ставит в
  очередь (`broadcasts`), а рассылает бот (`bot/broadcasts.py`) — пачками по 25 по
  возрастанию id, запоминая курсор и счётчики после каждой пачки. Копию API сразу
  присылает автору: так фото или видео один раз загружается в Telegram, и бот рассылает
  его по `file_id`, а Telegram заранее проверяет сообщение. Получатели — на момент
  создания рассылки, без автора, заблокировавших бота и заблокированных. Сегменты
  (`all`, `active_7d`, `active_30d`, `never_opened`) — ключи в `constants.py` и ветки в
  `repository._segment_condition`; новый сегмент (например, подписчики) добавляется там.
- **Отзывы** из настроек сохраняются в `reviews` (не больше 5 за сутки на пользователя).

### Авторизация
Каждый запрос несёт `Authorization: tma <initData>`. Подпись проверяется при
**каждом** запросе по алгоритму Telegram Web Apps; дополнительно ограничен возраст
подписи (`TMA_AUTH_TTL_SECONDS`). Без валидной подписи — `401`. Доступ к привычкам
всегда ограничен владельцем (`task.user_id` = пользователь из подписи): чужая
привычка для API не существует (`404`).

### Защита от злоупотреблений
- **Размер тела** — не больше 64 КБ (`BodySizeLimitMiddleware`): FastAPI читает тело
  до проверки авторизации, поэтому без предела анонимный POST любого размера
  разворачивался бы в памяти. Исключение — путь создания рассылки (`/admin/broadcasts`,
  до 50 МБ под видео): его форму обработчик разбирает сам, уже после проверки прав, а не
  объявленными параметрами `Form`/`File`, которые FastAPI читает до зависимостей.
- **Частота запросов** — token bucket на пользователя (`ratelimit.py`, ключ — id из
  проверенной подписи, а не IP: за прокси и туннелем адрес у всех один). Сверх лимита —
  `429` с `Retry-After`. Состояние — в памяти процесса.
- **Число привычек** — не больше 50 на пользователя: ограничивает и рост базы, и шквал
  напоминаний одному пользователю в одну минуту.
- **Тяжёлые справочники не блокируют сервер.** Каталог поясов и поиск города —
  чистый CPU (до десятков миллисекунд), поэтому `GET /meta/timezones` выполняется в пуле
  потоков, а цикл событий тем временем обслуживает остальные запросы.
- **Секреты не попадают в логи.** Токен бота — `SecretStr` (в repr настроек скрыт), а
  loguru настроен с `diagnose=False`: иначе трейсбэк печатает значения переменных, в
  том числе URL запроса к Bot API с токеном (так и случилось в логах прежнего бота).
- **Документация API** по умолчанию не публикуется (`TMA_DOCS_ENABLED`), API и
  фронтенд слушают только `127.0.0.1` — снаружи они доступны через nginx или туннель.

## Обработка ошибок
- API отдаёт ошибки в едином формате `{"error": {"code", "message"}}` с осмысленным
  HTTP-статусом (и для ошибок маршрутизации Starlette: `404`, `405`, `413`);
  непредвиденные исключения логируются (метод, путь, стек без значений переменных),
  наружу уходит обезличенное сообщение. `/health` проверяет и базу (`503`, если она
  недоступна).
- Фронтенд: у каждого запроса таймаут 15 секунд, а ошибка отрисовки показывает экран
  с кнопкой перезапуска (`ErrorBoundary`) вместо пустой страницы.
- Бот логирует необработанные исключения глобальным `dp.errors`; сбой настройки
  меню при старте не мешает работе.
